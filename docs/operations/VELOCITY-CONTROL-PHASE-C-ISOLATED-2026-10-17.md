   - Guards: named target, operator approval and maintenance window, authentic task fingerprint / process lineage, safe scheduled-task restart policy, no duplicate JVM family, unaffected sibling proxies, audit availability, zero verified players for stop/restart, authenticated graceful shutdown bridge, old process generation gone, **independently proven** free Java TCP + Bedrock UDP ports, a distinct newly attested process pair, and new Java TCP / real RakNet replies.

   - Supported *message vocabulary only*: status / prepare_shutdown / confirm_shutdown. **No listener or Velocity shutdown operation exists**.
   - This HMAC prototype **does not substitute for user authorization, local IPC peer attestation, player-count proofs or task-owner verification.** A future secure broker must source keys from protected per-proxy OS secrets and prove peer identity before accepting messages.
3. Automated tests: nine target/action happy-path simulations always `LiveAuthorized=false`; missing approval, player present, unsafe scheduler, wrong task, sibling drift, missing old process, empty Windows port provider, same-generation restarts, unhealthy Java/RakNet, timeout, replay and forged HMAC/cross-proxy scopes reject; concurrent replays accept exactly once.

## Phase C supplementary synthetic Windows Task Scheduler definition assessment

Added `internal/velocitylifecycle/scheduler_policy.go` and its table-driven tests. The pure Go parser accepts at most 64 KiB of **caller-supplied synthetic XML bytes** in the official Windows Task Scheduler namespace, with no `os`, `os/exec`, Task Scheduler APIs, process enumeration, file reads, filesystem writes or network calls.

The parser checks only structural assertions: exact `wild|playground|other` proxy target, one Windows `Exec` action with `java.exe`, relative `-jar velocity.jar` and matching directory suffix; SYSTEM/service-account principal; `RestartOnFailure.Count`, including an explicit **999 attempts** hazard. Negative regression fixtures include mismatched target directory, PowerShell/foreign Java action, additional COM action, wrong principal, missing/malformed restart count, empty input, unknown proxy ID, fake XML namespace and oversized payload. Additional adversarial fixtures reject UNC and relative executable paths, arbitrary directory-suffix matches, duplicate `-jar` switches and unsafe `MultipleInstancesPolicy` modes (`Parallel`, `StopExisting`, or missing instead of `IgnoreNew`). These are strictly in-memory classifications: a correctly shaped task XML still provides **no proof that a particular task actually owns a live Velocity JVM**. This is an isolated verification of guard logic and **does not read the user's Windows Task Scheduler**.

## Required bridge-to-runtime architecture before any future operational attempt

1. **Immutable operator authorization:** verify a locally authenticated GSC operator with an explicit per-proxy action, short-lived maintenance window, one-time challenge and action confirmation; no unattended remote kill capability.
2. **OS-authenticated local peer:** constrain to a Windows named pipe with an allowlisted SID/ACL or equivalent OS-backed peer identity. Bind the per-proxy session to a fresh child JVM generation; loopback TCP alone does not prove peer identity.
3. **Controlled secret management:** independent random per-proxy HMAC keys stored outside repo and protected by OS ACL/DPAPI, expiry/rotation and replay prevention across bridge restarts. Never include a forwarding secret or Floodgate key in this channel.
4. **Player-aware lifecycle:** prove player count exactly zero immediately before graceful shutdown; reject if clients appear, authentication is uncertain, or requests race with generation changes. Ensure warning/countdown policy is operator-approved.
5. **Verified scheduler semantics:** correlate the exact Day10 Windows Task Scheduler instance with parent and child process tokens, verify restart-on-failure policy and explicit stop suppression, then independently prove both process absence and port release. A plugin shutdown ACK is not proof of process exit.
6. **Post-start independent checks:** verify genuinely new JVM parent/child generation plus Java status and RakNet packets for the correct proxy without interpreting missing TCP provider rows as a healthy or stopped process; test remaining two sibling proxy generations unchanged.
7. **Disposable Windows VM rehearsal:** test real Task Scheduler auto-restart races, orphaned child JVMs, wrong owners, slow startup, player-present declines, expired requests, rollback and crash recovery before any live maintenance. No real test data or backed-up worlds may be mutated as a shortcut.

Until these have independently verifiable implementations and security review, **no Canary/Stable release may advertise functional Velocity stop/restart support**. A green isolated simulation is not an OS operation permit.

### Added source-only implementation

1. `internal/velocitybridge/challenge.go`: per-process `ChallengeVerifier` issues cryptographically unpredictable, fixed 20-second, operation/target/generation-bound server challenges and requires a signed matching challenge exactly once. Its issued-challenge ledger starts **empty** on every verifier restart; replaying a previously captured, valid HMAC envelope on a freshly initialized verifier therefore fails closed. A bad matching MAC consumes the challenge. Issuance is memory- and time-bounded; all unknown actions are denied. The legacy `Verifier.VerifyOnce` remains a lower-level authenticated-envelope primitive, **not sufficient alone for production against process-restart replay**.
2. `internal/velocitybridge/frame.go`: bounded 4-byte big-endian length-prefixed JSON framing for challenge and signed response, hard max 2048 bytes. Rejects truncated/oversized/duplicate-key/unknown-field/noncanonical-shape messages. Accepting a frame never authenticates the OS peer or authorizes start, stop or restart. In-memory duplex pipe fixture covers challenge → response → single-use verification and a simulated verifier restart.
3. `internal/velocitypeer/peer_windows.go`: Windows-only read-only `GetNamedPipeClientProcessId` + `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetProcessTimes` + `GetExitCodeProcess` proof. Keeps a **query-only process HANDLE** open to pin PID reuse, records the OS creation FILETIME in memory, rechecks the pipe client PID and denies closed or mismatching generations. No local IPC broker/listener, task/process modification, handle duplication, Java JAR write, or CLI command is implemented.
4. `internal/velocitypeer/*_windows_test.go`: unit tests of current CI process creation-time pinning, invalid or disconnected handles, and a **single randomly named test-local Win32 named pipe** whose client and server both live in the GitHub Windows runner test process. The pipe uses `PIPE_REJECT_REMOTE_CLIENTS`, creates no service, and closes all test handles.
5. `.github/workflows/system-ci.yml`: adds the Windows peer package to Go Race testing. The previous CI-only failing dummy task never demonstrated automatic restart despite completing cleanly: therefore the repeatedly executed 105-second **non-proving** probe was removed from routine System CI. The *proven* disposable `RestartOnFailure.Count=999 → override zero → original 999` task-definition restore test remains. The real scheduler crash-recovery and graceful stop behavior remain explicitly **unverified**.

## Phase D4 — Disposable interprocess Win32 evidence (CI ONLY; no host change)

The new `internal/velocitypeer/interprocess_windows_test.go` creates **one temporary Windows named pipe and a test-owned separate child process**, with no task, GSC instance, Velocity JVM, Minecraft ports or operator files. It uses Windows `GetNamedPipeClientProcessId` to bind the server-side pipe to the OS-reported child PID, holds a read-only `OpenProcess` HANDLE and verifies kernel creation time, and queries the child's OS token user SID. It then exchanges a strict length-bounded, single-use challenge/response over the actual pipe and checks that replay against a restarted verifier fails closed. The test child terminates after receiving a successful one-byte acknowledgment; the test process closes its pipe, process and token handles.

The default Windows named-pipe security descriptor grants unexpectedly broad **read** access, so the disposable interprocess test has been hardened to create its pipe with an explicitly **protected DACL** built by `internal/velocitypeer/pipe_acl_windows.go`. `NewRestrictivePipeACL` takes exactly one or two independently selected **account/service** SIDs. It validates canonical forms, rejects anonymous and broad-group identifiers (Everyone, Authenticated Users, builtin Users/Administrators etc.), builds `D:P` SDDL and passes the resulting native security descriptor only to its own `CreateNamedPipeW` test call. The helper does **not** change a filesystem, firewall, existing pipe, process, scheduled task or Windows account ACL. This is a source-only construction primitive, not a running broker.

**Limits:** A same-user process with the allowed SID is not automatically an authorized application. A real integration must separately pin the actual GSC host and Velocity plugin binary/generation and have protected per-proxy HMAC keys, no replay, admission freeze, zero-player/drained-inflight proof, reversible scheduler policy and explicit maintenance approval. Windows runner SID and DACL behavior must not be assumed equivalent to the server PC without a separate read-only/controlled test. Any simulated OS-PID/SID+HMAC success must remain `LiveAuthorized=false`.

The *negative* Task Scheduler crash-retry CI observation remains unresolved and is not part of routine release success. GSC v4.5.2 Canary lifecycle actions are still **disabled**. No Java plugin installation, backend modification, server restart, auth key export or production ACL change was made.


## Phase D5 — Windows per-proxy HMAC key safety (source-only)

Added `internal/velocitybridge/keys_windows.go` to reuse GSC's existing Windows DPAPI implementation **only through a stricter, purpose-specific wrapper**:

- `GenerateUserProtectedProxyKey(wild|playground|other)` creates a fresh 256-bit CSPRNG HMAC key and returns **opaque `dpapi-u:` ciphertext only**, without file write, console output, release asset, registry edit or Java integration.
- `OpenUserProtectedProxyKey` rejects unknown targets, cross-proxy substitutions, tampered/truncated blobs, plaintext legacy fallback, `dpapi-m:` machine-scope ciphertext and malformed key sizes. The generic legacy `securestore.UnprotectString` can accept plaintext, but that behavior is explicitly **not allowed** on this new key path. On non-Windows, `keys_other.go` fails closed rather than using the old pass-through securestore behavior.
- Windows CI tests real **current-user** DPAPI roundtrip and reuse of the unsealed key for the HMAC challenge/response test. Only transient **test-runner** protected blobs are created, and secret bytes are not emitted to GitHub logs.

This is **not** a production secret provisioning workflow. The user-protected key is decryptable only under the compatible Windows security context; the separate Velocity JVM account may differ. A production installer must determine and authorize exactly which OS principals will run GSC and each proxy, apply matching NTFS ACLs, safely deliver or derive each JVM's per-proxy key without logging or exposing it, and rotate keys on process/account compromise. This remains a design gate; **do not ask the operator to export or upload a real secret**. No production DPAPI key has been created or saved by this source-only phase.

Formal remainder before any start/stop/restart feature claim: authenticated GSC↔Velocity runtime transport with named-pipe DACL and process-generation binding, Java bridge challenge implementation, player admission fencing and zero/in-flight login proof, fail-closed local operator approvals, scheduler recovery semantics independently reproduced in isolated Windows VM, full Java+Bedrock actual login tests and explicit Canary rollout approval. All production actions stay **NO-GO**.
