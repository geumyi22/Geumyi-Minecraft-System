# GSC 5.2.0 · 실제 PC 검증 체크리스트

대상은 Windows 11 x64의 GSC 5.2.0과 GMS Operating Mode 3.0.1입니다. **각 칸은 운영자가 해당 PC에서 직접 확인한 뒤 표시하세요.** 서비스가 없는 관리 PC처럼 적용할 수 없는 항목에는 ‘해당 없음’과 이유를 적으세요. 재부팅과 운영 설정 변경은 운영자가 승인한 점검 시간에 진행합니다.

## 1. 변경 전에 기준 상태 남기기

- [ ] 지난 백업의 시간과 위치를 확인했다. 월드·플레이어 데이터·플러그인 설정을 복구할 수 있는 백업이 있으며, 개발 자료와 v2 원본의 보관 위치도 확인했다.
- [ ] 서버 운영 계정과 설치 경로를 확인했다. 다른 관리 PC를 사용할 경우 서버 PC와 관리 PC에 대해 별도 기록을 만들었다.
- [ ] Windows 서비스의 Host 시작 유형·실행 상태, 현재 계정의 Client 로그인 자동 실행, 예약 작업의 활성 트리거·다음 실행 시간, 별도 감시 프로그램의 실행 상태를 기록했다.
- [ ] 비교할 파일을 정했다. 예를 들어 정상 종료 후의 월드 파일과 플레이어 데이터, 설정, 개발 자료의 경로·크기·해시를 별도 위치에 기록한다. 실행 중인 월드의 정상 저장에 따른 차이는 종료 전후를 나누어 기록한다.
- [ ] GMS와 무관하게 평소 실행하는 Java 프로그램이나 다른 서비스가 있다면 이름·경로와 상태를 기록했다. 프로그램이 없는 PC는 해당 없음으로 적었다.

## 2. 열기·권한·취소

- [ ] 표준 권한에서 독립 EXE를 열어 **GMS Operating Mode 3.0.1** 창과 검사 결과를 확인했다. 공식 배포 파일과의 대조 결과를 기록했다.
- [ ] Client가 있는 PC에서 **⚠ 위험 작업 → GMS 운영 모드 → 새로고침**을 실행했다. **GSC Host 서비스 시작 유형**과 **GSC Client 로그인 자동 실행**을 Windows의 기준 상태와 대조했다.
- [ ] **운영 모드 관리자 열기**, **수동 전환 미리보기**, **기존 설정 복원 확인**이 해당 PC의 창을 여는지 각각 확인했다. 이미 실행 중인 창이 있다면 정상 종료한 다음 다음 버튼을 점검했다.
- [ ] 일반 권한의 미리보기를 취소하고, 이어서 Windows 권한 요청도 취소해 보았다. 이전에 기록한 시작 설정이 유지됐다. 같은 계정으로 권한을 승인했을 때 관리자 창에서 최종 목록을 다시 볼 수 있었다.
- [ ] **자동 실행**의 **식별 근거**와 **실행 상태 · 확인 필요**에 표시된 폴더를 확인했다. 필요한 전용 서버 폴더만 추가했다. 다른 Java, 다른 Windows 계정, 복합 스크립트 등 확인이 필요한 항목을 별도로 기록했다.

## 3. 승인된 수동 전환과 정상 종료

- [ ] 플레이어에게 점검을 공지하고 접속 종료를 확인했다. **수동 모드 전환** 미리보기의 각 이름과 예정 변경을 기록한 뒤 확정했다.
- [ ] 완료 후 **백업 · 복구**의 복원 대상 수와 각 상태, 진단 로그 위치를 기록했다. 다시 검사할 때 이미 차단한 항목이 새 변경으로 반복 제시되는지 확인했다.
- [ ] **Host 정상 종료**를 요청했다. 서버의 저장 완료와 Host·Agent 종료를 실제 로그와 프로세스에서 확인했다. 거절되거나 시간이 초과되면 이유를 기록하고 원래 GSC에서 상태를 확인했다.
- [ ] 독립 Minecraft 서버는 원래 콘솔의 `stop`, 독립 Velocity는 해당 콘솔의 `shutdown`으로 종료했다. GSC Client는 트레이에서 종료했다. 무관한 Java 프로세스와 다른 서비스의 상태를 기준 기록과 대조했다.
- [ ] 이전 지점에서 저장한 데이터와 구분해 **정상 종료 직후**의 보존 기준을 기록했다. 아래 재부팅 관찰이 끝날 때까지 서버와 Client의 의도적인 수동 시작을 보류했다.

## 4. 재부팅 후 자동 시작 관찰

로그인 직후에는 GSC Client를 직접 열기 전에 Client 자동 실행부터 관찰하세요. GUI에서 확인할 때는 먼저 독립 EXE를 열어 관찰하고, 본인이 수동 실행한 프로그램과 시간을 기록하세요.

| 시점 | 점검할 내용 | 실제 시각·관찰값·근거 |
|---|---|---|
| 재부팅 직전 | Host·Client·Minecraft·각 Velocity·StatusAgent 상태. 남은 예약 작업과 다음 실행 시각 | |
| 로그인 직후 | 자동으로 뜬 Client·트레이 아이콘, Host 서비스의 실행 상태, 서버·프록시·Agent의 PID 및 설치 경로 | |
| 지연 시작 시간이 지난 뒤 | Host와 예약 작업 재확인. 독립 EXE의 **백업 · 복구**에서 새 부팅 세션과 차단 상태 대조 | |
| 다음 예약 이벤트 또는 Discord 일일 요약 시각 | 원래 트리거 시각에 작업이 시작됐는지, 상태판이 갱신됐는지, 새 일일 요약이 전송됐는지 기록 | |
| 같은 시점의 데이터와 무관한 앱 | 정상 종료 직후 표본과 월드·플레이어·설정·개발 자료 대조. 비교 대상 Java·서비스의 정상 동작 확인 | |

해당 일정 시각이 아직 오지 않았다면 날짜와 함께 **미검증**으로 남기세요. 기존 Discord 메시지가 채널에 남아 있는 것과 새 메시지·갱신이 발생한 것은 구분해 기록하세요.

## 5. 수동 시작·복원·업그레이드

- [ ] 승인된 시간에 **Host 수동 시작**을 눌렀다. Host 실행 상태와 실제 기동된 서버·Agent·Discord 기능을 확인했다. 별도 프록시는 원래 제어 화면에서 필요한 것만 시작했다.
- [ ] 테스트 계정으로 접속해 기존 월드와 플레이어 데이터, 사용하는 연결 경로를 확인했다. 개인 서버, 프록시 경유, Bedrock/GSCM 원격 연결 등 해당 PC에서 평소 쓰는 구성만 결과를 적었다.
- [ ] 원상 복구 점검을 승인한 경우 **기존 모드 복원**에서 목록을 확인하고 적용했다. 기준 기록과 서비스 시작 유형(지연 여부 포함), Client 등록 상태, 예약 트리거, 시작 폴더와 복원 대상 수를 대조했다. 즉시 발화한 예약 작업이 있으면 시각을 기록했다.
- [ ] **중단된 작업 복구**나 충돌 메시지가 실제로 나타난 경우 원문과 로그를 기록하고 같은 계정에서 복구 후 재검사했다. 운영 PC에서 장애를 일부러 만들지는 않는다. 발생하지 않은 중단 복구는 ‘미검증’으로 적는다.
- [ ] 설치·업그레이드까지 승인한 경우 현재 역할과 버전을 기록했다. 복원 기록 때문에 Setup이 보류되면 같은 PC·계정에서 복구 또는 원상 복원 후 진행했다. 서버 PC는 실행 중인 이전 Host의 정상 상태를 확인했다.
- [ ] 점검 종료 후 원하는 최종 상태를 선택했다. 수동 운영을 계속하는 경우 Setup 또는 복원 이후 **다음 재부팅 전** 수동 모드를 다시 적용하고, 종료 대상만 정상 종료했다. 원래 운영으로 돌아간 경우 복원한 시작 설정을 다시 확인했다.
